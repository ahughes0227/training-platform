# Compute Engine queue service templates

These files are deployment templates. They do not install or start anything and do not establish readiness for a particular VM. Review them against the pinned systemd, Docker, NVIDIA Container Toolkit, service account, and filesystem versions on the target host before installation.

`defect-queue-api.service` runs the local Unix socket API as a dedicated unprivileged UID. `defect-queue-worker.service` runs the supervisor separately. The current worker needs host-root authority because it uses the privileged container engine and prepares output directories for the trainer UID. Docker daemon access is equivalent to host-root control; systemd sandbox options do not remove that authority. Restrict the worker's code, config, engine socket, and host login access accordingly.

The templates assume these separately provisioned identities:

- `defect-queue-api`: API process UID.
- `defect-queue-state`: private group shared by the API and worker for SQLite, journals, and queue evidence. The worker process UID is root (UID 0), as required by the current executor's Docker and attempt-directory ownership model.
- `defect-queue-operators`: operator group for the Unix socket only. It must not be a member of `defect-queue-state`.
- A dedicated nonzero trainer UID/GID, distinct from API and operator identities.

Pre-provision `/var/lib/defect-platform` as `root:defect-queue-state` mode `2770`, and verify SQLite/database sidecars inherit the shared group with mode `0660`. The root worker and API UID must be the only principals that can change queue state. Keep `/etc/defect-platform` root-owned and not group/world writable. Install the completed config as `root:defect-queue-state` mode `0640` so both service UIDs can read it; install the trainer credential file as `root:<trainer-group>` mode `0440`. Do not put credentials in the YAML file. Configure `state_group_id` and `socket_group_id` to the actual numeric GIDs of `defect-queue-state` and `defect-queue-operators`; keep the socket mode `0660` and its parent directory non-writable by operators.

Copy [queue-config.example.yaml](queue-config.example.yaml) to `/etc/defect-platform/queue.yaml`, replace every `REPLACE_...` value with the current approved record, and validate it with the same application revision before enabling either service. The example intentionally fails validation and must never be used as-is. Numeric cost limits, actual boot-disk free bytes/inodes and headroom, VM/boot ID, GPU UUIDs, exact driver/toolkit/engine versions, image compatibility, backup destination and restore evidence, allowed OS UIDs, isolated trainer network, and least-privilege credentials require measured owner evidence. The user's nominal 500 GB disk size alone establishes none of those values.

Install the application at `/opt/defect-training-service` and ensure `/usr/local/bin/defect` points to its pinned environment. The `defect train queue` CLI must be registered by the same reviewed code revision. The worker requires the Docker Engine and GPU observers; its `docker` CLI socket access is an explicit privileged host boundary. The API service does not receive the engine socket. The trainer receives only the configured GPU request, immutable request file, per-attempt output/scratch paths, and readonly artifact credential mount. A named Docker network is mandatory; separately prove it denies the GCE metadata endpoint and permits only the artifact/tracking traffic required by the approved workload.

The API creates `/run/defect-platform/queue.sock`. Its runtime directory is mode `0711`, while the socket is owned by the service and configured operator group with mode `0660`; peer UID authorization remains authoritative. `RuntimeDirectoryPreserve=no` lets systemd clean this volatile directory across a normal service stop/restart. If startup reports an existing socket, stop the unit and inspect the exact path and owning process before cleanup. Confirm there is no live queue API process, verify the path is a socket inside `/run/defect-platform`, then remove only `/run/defect-platform/queue.sock` and restart. Never wildcard-delete runtime paths or replace a non-socket file.

The queue database and the runtime socket are separate: a clean API restart does not clear accepted queue state. Backups must be application-consistent and copied to the configured off-VM destination. Before unattended operation, test a restore and reconcile any container identities. Do not use global Docker prune commands; cleanup must preserve active/certified images and attempt evidence. Local log limits are set on each queue-owned container, but host journal retention and queue-evidence retention still need explicit disk-capacity review.

Review installation and restart behavior without starting training. A future deployed acceptance run must separately verify API peer-UID allow/deny behavior, worker restart/reconciliation, socket recovery, boot identity, GPU/runtime readiness, metadata denial from inside the trainer network, storage quotas/headroom, backup restore, and shutdown/cancellation behavior. No live VM action or service installation is authorized by these templates.
